## 1. 추천하는 결정

**게임 경험과 런타임 구조를 재설계한다. 대표 차량 한 대와 해안 서킷 한 개로 완결되는 아케이드 레이싱을 먼저 만든다.**

목표 경험은 “출발하자마자 차가 읽히고, 직선에서 200km/h 이상을 체감하며, 코너를 익힐수록 기록이 줄어 다시 달리고 싶어지는 게임”이다. 차고는 이 경험을 뒷받침하는 독립 정비 공간으로 만든다.

Three.js·Rapier·Vite는 우선 유지한다. 검증된 에셋 원본·출처·저장 데이터는 보존하고, 거대한 런타임·덧붙인 UI·임시 차량 보정·평면 코스 구조는 재설계한다. 이전의 ‘차량 컬렉션부터 확장’ 계획보다 주행·카메라·대표 장면을 앞에 둔다. 기존 문서는 과거 이력으로 남긴다.

## 2. 조사 범위와 확인 수준

- 로컬 소스, 차량/코스 데이터, 패키지, 검사 스크립트, 기존 계획을 직접 읽었다.
- 실제 Three.js 곡선 생성 코드로 길이를 계산했다. 하버 링 약 810.0m, 알파인 스프린트 약 755.3m다.
- 앞선 동기화에서 커밋 기준점은 최신이지만, 충돌한 `App.jsx`·`styles.css`는 로컬본이 선택됐다. 따라서 배포판과 로컬은 같은 게임 화면이 아니다.
- 원격에서 받은 `car-body.js`·`city-dressing.js`는 로컬 src import 검색에서 사용 경로를 찾지 못했다. 내려받은 개선 코드가 실제 화면에 연결됐다는 뜻은 아니다.
- 이전의 220km/h 검사 결과는 별도의 물리 검사용 월드에서 나온 값이다. 모든 차종과 실제 코스의 조작 품질을 보장하지 않는다.
- 이번 조사에서 브라우저 연결이 실패해 새 플레이 영상·화면은 직접 검증하지 못했다. 기존 사용자 캡처와 코드 근거를 구분했다.
- [사용자 지정 Threads 영상](https://www.threads.com/@choi.openai/post/Dc4vxEmDRj4/media)은 미디어 조회 실패, 해당 게시물의 공개 검색 실패, 브라우저 도구 연결 실패로 **미열람**이다. 제작 모델·엔진·개발 시간·게임 내용을 추정하지 않는다.

후속으로 사용자가 제공한 AFTERLIGHT 캡처 3장을 직접 확인했다. 이제 재질·조명·공간 밀도의 기준은 15절의 캡처 분석을 따른다. 원본 영상의 움직임·성능·구현 방식은 여전히 미확인이다. 이번에는 분석/계획 문서만 작성하고 게임 구현·커밋·운영 배포는 하지 않는다.

## 3. 현재 구조의 문제와 근거

| 발견 | 확인 근거 | 재설계 방향 |
|---|---|---|
| 책임이 한 파일에 집중 | `src/racing-runtime.js` 166,659바이트, 698줄에 차고·트랙·물리·AI·렌더·오디오가 혼재 | 짧은 줄 수와 달리 긴 한 줄 코드가 많다. 기능별 소유권과 생명주기를 분리한다. |
| 화면과 엔진 결합 | `App.jsx`가 런타임 생성/파괴·화면·기록 저장을 함께 처리. `main.jsx`는 CSS 4종을 순서대로 import | 화면별 스타일 범위와 상태 전환을 명시한다. |
| 평면 곡선 중심 코스 | 각 코스 11개 X/Z 점. 런타임 625줄에서 모든 Y가 0 | 높이·폭·뱅킹·노면·구간 역할을 가진 코스 명세로 바꾼다. |
| 도로 폭만 늘려서는 해결 안 됨 | `ROAD_HALF=11.5`, 실제 생성 폭 23m | 차 크기·카메라·곡률·시야를 함께 검토한다. 좁다는 체감에 무조건 확폭하지 않는다. |
| 고속 목표와 공간 규모 | 일정하게 220km/h라는 가정의 1랩은 13.3초·12.4초 | 실제 완주 시간이 아닌 규모 비교다. 충분한 직선·제동·탈출 구간을 설계한다. |
| 프레임 의존 시간 | 697줄 `dt=Math.min(.033,rawDt)`, 프레임마다 한 번 `updatePhysics(dt)` | 지속 20fps라면 현실 1초당 약 0.66초 진행 가능. 누적 고정 스텝과 렌더 보간으로 재설계한다. |
| 여러 주행 보정이 중첩 | 649~652줄 속도·제동·드리프트·노면 처리에서 속도/각속도 직접 변경. 주행 보조는 회전도 변경 | 아케이드 보정의 접지·충돌 책임을 명확히 하고 단일 차량 컨트롤러로 수렴한다. |
| 외형과 물리 규격 불일치 가능 | `replaceCar`는 차종별 외형 길이 정규화, `createVehicle`는 공통 박스·휠 좌표 | 외형·바퀴·충돌을 같은 차량 명세에서 만든다. |
| 불안정한 재질 판정 | 96~133줄 이름 정규식으로 차체·유리·램프 분류, 색·불투명도 강제 변경 | 아틀라스 모델은 이름만으로 부위를 구분하기 어렵다. 모델별 명시적 매핑을 둔다. |
| 바퀴 회전 처리 | `syncVehicle`에서 `wheel.rotation.x-=speed*.018` | 시간·후진 부호·축·반경과 실제 서스펜션 상태를 반영한다. |
| 검사와 품질 평가 혼동 | `check-visual-quality.mjs`·`check-physics.mjs`는 주로 문자열 포함 검사 | 구조 존재 검사로 분류하고 실제 화면/주행 검증을 별도로 둔다. |
| 게임과 분리된 동역학 검사 | `check-drive-dynamics.mjs`는 런타임 import 없이 별도 월드·보정 구현 | 게임이 쓰는 컨트롤러 자체를 import해 검사한다. |

과거 작업의 에셋 관리·저장·물리 실험은 활용할 수 있다. 다만 장식 개수나 검사 문구 수를 완성도 기준으로 삼지 않는다.

## 5. 게임 방향 선택

| 방향 | 장점 | 부담 | 판단 |
|---|---|---|---|
| 스타일라이즈드 해안 서킷 | 고속 주행·추월·한 장소의 미술 품질에 집중 | 차·카메라·코스 조합을 세밀하게 제작해야 함 | 추천 |
| 미니어처 탑다운 카트 | 디오라마 전체가 잘 보이고 단순 에셋에 적합 | 후방 추적 고속 주행과 경험이 달라짐 | 영상 확인 후 대안 |
| 사실적 오픈월드 | 차량·도시·경관 확장 가능 | 고품질 차량, 월드, 교통, 스트리밍 부담이 동시 발생 | 첫 완성 범위에서 제외 |

후속 캡처를 반영한 추천 스타일은 ‘비가 갠 산업 항구의 모터스포츠’다. 어두운 청록·회색 구조물에 따뜻한 측면광, 부분적으로 젖은 노면, 오래된 벽돌·금속·콘크리트를 조합한다. 차체·타이어·유리와 도로 경계는 명료하게 구분한다. 해안 서킷의 주행 설계는 유지하면서 피트/창고 구역의 미술을 이 기준으로 제작한다. 구체적인 적용안은 15절에 정리한다.

대표 차량은 스포츠 GT 한 종류다. 현재 GLB 후보의 전/측/후면을 중립 조명에서 검수하고 가까운 카메라에 적합한 모델을 고른다. 부족하면 대표 차체의 별도 제작을 비교한다. 가까이 보이는 주인공은 별도 제작하고 배경은 CC0 프롭으로 구성할 수 있다.

## 6. 첫 완성 범위와 화면 흐름

첫 완성본은 **GT 1대 / 신규 코스 1개 / 타임어택 / 개인 고스트 / 즉시 재시작 / 독립 차고**다. 이후 AI 3대와 3랩 경쟁 모드를 더한다.

```text
홈: 대표 차량과 서킷 배경
  ├─ 바로 달리기 → 카운트다운 → 1랩 → 기록 차이 → 즉시 재도전
  ├─ 차고 → 차량 확인·컬러·시험 주행 → 바로 달리기
  └─ 설정 → 입력·사운드·화질
```

- 기본 차량·코스를 미리 골라 첫 주행 전에 여러 선택 화면을 거치지 않게 한다.
- HUD는 시간·랩/섹터·속도·기록 차이 중심. 경쟁 모드에서 순위를 추가한다.
- 한국어 행동 문구, 한글 본문 글꼴 1종, 고정폭 숫자로 정리한다.
- 가속·제동·조향·핸드브레이크·재시작을 분리한다. 자동 가속은 선택 설정이다.
- 모바일은 가로 주행을 기준으로 별도 검증하고, 세로 화면은 회전 안내와 접근 가능한 설정을 제공한다.
- 차고는 실제 작업대·공구·타이어·피트 출구가 있는 독립 씬이다. 차량 앞을 링·패널·장식으로 가리지 않는다.
- 학습/배송은 제외한다. 컬렉션 확장, 경제, 시즌, 멀티플레이, 파괴, 트랙 에디터는 후속 후보다.

## 7. 차량·물리·카메라 설계

### 차량 명세

`VehicleSpec`에 전방 축, 단위/길이, 바닥 피벗, 네 바퀴 경로·축·반경·휴지 자세, 충돌 크기·무게중심, 재질 역할을 명시한다. 자동 바운딩 박스는 검증용으로 쓰고 최종 조립 규칙은 차량별로 명확하게 정의한다.

중립 조명에서 원본 텍스처·법선·재질을 먼저 검사한다. 아틀라스 차량의 색 변경은 명시적 구역 마스크가 준비된 경우에 적용한다. [Three.js 색 관리](https://threejs.org/manual/en/color-management.html)를 기준으로 색 공간과 최종 출력 변환을 한 경로에서 관리한다.

### 주행 코어

- 누적 시간 기반 1/60초 고정 물리 스텝과 렌더 보간. 차량 컨트롤러와 World에 같은 dt 사용.
- 30/60/120fps 렌더에서 동일 입력을 동일 물리 틱에 공급. 최대 따라잡기 스텝 제한을 넘으면 타임어택 무효 표시. 숨긴 탭/포커스 상실은 일시정지.
- 가속·제동·횡방향 그립·드리프트 상태 전환을 하나의 컨트롤러에서 처리. 보정은 접지·슬립·충돌 상태에 따라 제한.
- 공중에서 지상 가속 보정이 차를 임의로 끌지 않게 한다. 직접 위치 변경은 재배치/리셋에 한정.
- AI는 플레이어와 같은 조향·가속·브레이크 입력 및 차량 스텝 사용.
- 초기 튜닝 목표: 기본 최고속도 220km/h, 선택적 부스트 250km/h, 0→100 약 4~5초, 100→0 약 40~55m. **현재 달성값이 아닌 신규 목표값**이다.

Rapier는 기반이며 조작감·카메라·경기 규칙까지 대신 설계하지 않는다. 시간/충돌 설정은 [공식 simulation structures](https://rapier.rs/docs/user_guides/javascript/simulation_structures/)와 [World API](https://www.rapier.rs/javascript3d/classes/World.html)를 기준으로 검토한다.

### 카메라와 속도감

- 차량 후면이 명료한 추적 카메라 하나부터 완성. 위치·시선 감쇠를 분리하고 코너 출구를 조금 앞서 바라본다.
- 차량과 카메라 사이의 장애물 충돌을 검사한다. FOV 변화·부스트 흔들림·충돌 흔들림은 독립 설정으로 둔다.
- 도로 표식·길가 기둥·근경 배리어 간격, 스키드, 엔진 부하·바람 소리를 함께 맞춘다.
- 16:9 화면의 차량 높이 점유율 16~22%를 시작값으로 검토한다. 제동 표지와 코너 출구를 가리지 않아야 한다.

## 8. 새 코스 초안: COASTLINE GP

길이 1.6~2.0km, 초안 1.8km, 목표 1랩 60~90초. 차도 기본 16m, 추월 구간 18~20m, 좁은 구간도 초기에는 14m 이상으로 검토한다. 기존 23m보다 숫자가 작아도 차량·카메라 비율과 코너 반경이 맞으면 체감은 달라진다. 폭은 대표 구간 실측 후 확정한다.

| 구간 | 길이 초안 | 주행 역할 | 시각 기준점 |
|---|---|---|---|
| 피트 직선 | 600m | 가속·부스트·200km/h 체감 | 출발 타워·피트·관중석 |
| 첫 코너 접근과 코너 | 200m | 제동·추월·탈출 | 200/150/100/50m 보드·런오프 |
| 해안 고속 코너 | 300m | 가속 유지 | 바다·등대·낮은 배리어 |
| 오르막 S | 250m | 조향 전환·접지 | 암벽·나무 군집 |
| 정상 연결부 | 150m | 시야 변화 | 항구 조망·난간 |
| 마지막 연속 코너 | 300m | 드리프트 선택·다음 랩 준비 | 피트 타워가 다시 보임 |

길이는 곡선 제작 후 실제 arc length로 재측정한다. 200m 표지의 위치는 코너 정점에서 접근 방향으로 측정해 필요하면 앞 직선에 놓는다. 최초에는 점프·루프를 넣지 않는다. 도로와 시야가 통과하면 고저차 약 8~15m와 완만한 경사·뱅킹을 조정한다.

`TrackSpec`에는 중심선 외에 거리별 폭·높이·뱅킹·노면·런오프·체크포인트·장식 구역을 담는다. 이 데이터에서 렌더 메시, 충돌체, 미니맵, AI 기준선, 게이트를 함께 생성한다.

피트·관중석은 구도를 고정하고 나무·기둥은 간격/시야 규칙으로 배치한다. 코너 안쪽과 탈출 시야에 여유를 둔다. 근경만 상세 에셋을 쓰고 항구·산은 저비용 원경으로 묶는다.

## 9. 경기·고스트·AI

- 순서가 있는 게이트 평면과 차량 이동 선분의 교차로 체크포인트 판정. 고속 프레임에서도 누락 방지.
- 역주행 출발선 통과·코스 지름길·리셋 직후 랩 획득 방지. 마지막 유효 지점 재배치와 기록 무효 정책 명시.
- 순위는 유효 랩 + 체크포인트 + 구간 내 투영 거리. 최근접 점만으로 랩을 올리지 않음.
- AI는 곡률 기반 목표 속도·전방 제동 계획·앞차 간격·추월 후보 차선을 사용. 차선 변경 대기시간 적용.
- 고스트는 충돌 없는 위치/회전 샘플의 시간 보간. `trackVersion`, `physicsVersion`, `carId`, 모드, 틱/시간 포함.
- 코스/물리 변경 시 옛 기록은 역사 데이터로 남기고 신규 기록과 직접 비교하지 않음.

## 10. 새 구현 구조와 보존 범위

```text
src/
  app/           화면·결과·설정
  game/core/     고정 스텝·입력·pause·자원 생명주기
  game/vehicle/  명세·컨트롤러·외형/휠 연결
  game/track/    명세·메시/충돌/게이트 생성
  game/race/     경기 상태·순위·고스트·AI 입력
  game/render/   재질·조명·카메라·화질
  game/garage/   독립 차고 씬
  game/audio/    엔진·타이어·충돌음
  data/          차량·코스·배치
  storage/       버전별 프로필/기록 이관
tests/
  simulation/    게임과 동일한 컨트롤러 검사
  browser/       실제 조작과 렌더 캡처
docs/evidence/   커밋·기기·설정별 검증
```

신규 코어는 TypeScript를 권장한다. 입력·단위·좌표·상태를 명시하기 위함이다. 기존 파일 전체 변환부터 시작하지 않는다. React는 화면, Three.js는 렌더링, Rapier는 물리에 책임을 둔다. 매 물리 틱의 상태 전체를 React로 복제하지 않는다.

| 대상 | 처리 |
|---|---|
| 에셋 원본·라이선스 | 보존, 대표 모델만 신규 로더로 도입 |
| 프로필·해금·기록 | 기존 키 보존, 새 버전/키를 만들고 이관 검증 |
| 기존 런타임 | 스냅샷 보존 후 기능별 신규 코드로 교체 |
| UI·CSS | 화면 구성과 스타일 범위를 새로 작성 |
| GitHub 차량/도시 모듈 | 비교 후보로 보관, 채택 시 실제 사용 경로 검증 |
| 유효한 에셋/번들 검사 | 유지·갱신 |
| 문자열 품질 검사 | 구조 검사로 분류, 완성도 판정에서 제외 |
| 기존 차 10종·코스 2개 | 원본 보존, 최초 신규 완성본에 일괄 투입하지 않음 |

엔진 교체만으로 문제를 해결할 근거는 없다. pmndrs 전체 포크는 다른 물리/상태/에셋 규약의 이식 부담을 만든다. Three.js·Rapier의 작은 신규 코어로 먼저 검증하고 그 단계에서 충족하지 못하는 요구가 확인될 때 엔진 대안을 재검토한다.

## 15. AFTERLIGHT 캡처를 반영한 그래픽 방향

### 관찰과 구현 추론의 구분

2026-09-05 사용자가 제공한 3장에는 AFTERLIGHT, The Common Line, The Rain Court 문구가 보인다. 비스듬히 내려다보는 카메라, 거친 벽돌 상단, 어두운 벽과 밝은 바닥, 웅덩이 같은 반사 영역, 배관·덩굴·작은 기계, 따뜻한 창문빛과 청록색 포인트를 관찰할 수 있다.

정지 캡처만으로 원본 엔진, 실시간 반사 방식, GI/레이 트레이싱 사용 여부, 실제 FPS, 사용 모델을 알 수는 없다. 아래 PBR·AO·반사 방식은 비슷한 인상을 내기 위한 **우리의 구현 제안**이다.

### 무엇이 이 장면의 품질을 만드는가

| 캡처에서 보이는 특징 | 레이싱에 옮길 방법 |
|---|---|
| 돌출된 벽돌·두꺼운 창틀·부서진 상단 | 가까운 피트 벽과 창고 외곽선에 실제 두께/모서리. 먼 벽은 노멀맵과 반복 모듈로 단순화 |
| 밝은 바닥과 어두운 벽의 대비·긴 그림자 | 일관된 방향광, 부드러운 주변광, 필요한 위치의 보조 조명. 차와 도로가 암부에 묻히지 않도록 조정 |
| 바닥 일부만 매끈하게 반짝임 | 아스팔트·젖은 콘크리트·웅덩이를 구역별 거칠기 마스크로 구분. 전체 도로를 거울처럼 만들지 않음 |
| 벽 하단·틈·물체 발치의 어두움 | 정적 AO/라이트맵과 접지 그림자. PC에서 화면 공간 AO를 추가 비교 |
| 회색·청록 중심, 적은 주황빛 | 차고/항구 구조물의 재질 팔레트 통일. 안전 표지·차량·브레이크등은 구분되는 색 사용 |
| 조밀한 벽 주변과 비어 있는 중앙 통로 | 장식은 트랙 바깥과 피트 구역에 집중. 운전 경로·코너 출구는 시각적으로 비워 둠 |
| 겹겹의 건물과 먼 곳의 흐림 | 근경·중경·원경을 구분한 배치와 안개. 도로 제동 시야를 가리지 않음 |

### 구현 가능성과 비용 배분

브라우저에서 유사한 재질/조명 분위기를 목표로 삼을 수 있다. Three.js의 [MeshStandardMaterial](https://threejs.org/docs/pages/MeshStandardMaterial.html)은 거칠기·금속성·노멀·AO·환경맵을 지원하며, [GTAO 예제](https://threejs.org/examples/webgl_postprocessing_gtao.html)와 [환경맵 예제](https://threejs.org/examples/webgl_materials_envmaps.html)를 제공한다. 이것이 동일한 성능과 완성도를 자동으로 보장하는 것은 아니다.

원본 캡처는 가까운 벽으로 둘러싸인 제한된 공간과 높은 카메라다. 200km/h 후방 추적 시점은 원거리 시야, 움직이는 그림자, 반사 변화, 에셋 로딩까지 검증해야 한다. 목표 해상도·기기에서 측정하기 전에는 ‘전 코스 같은 품질로 60fps’를 약속하지 않는다.

- PC: 환경맵·거칠기 마스크를 기본으로 하고 필요한 대표 구역에만 선택적 반사를 검토한다. 환경맵만으로 움직이는 차와 건물의 정확한 바닥 반사가 생기지는 않는다.
- 평면 반사/SSR은 추가 렌더 비용·화면 밖 정보 누락·경사 대응을 실제 주행에서 비교한 뒤 채택한다. 원본 캡처가 이 기법을 썼다고 단정하지 않는다.
- 모바일: 정적 조명/AO, 낮은 그림자 해상도, 단순한 반사로 같은 색·형태·명암 인상을 유지한다.
- 벽돌 하나마다 별도 물리·드로우콜을 만들지 않는다. 반복 배치/메시 병합과 단순 충돌체를 사용한다.
- 무료 에셋은 배경 프롭 중심으로 선별한다. 대표 차량·피트 입구·가까운 벽은 이 미술 방향에 맞는 모델/재질 제작이 필요할 수 있다.
- 젖어 보이는 표현과 실제 젖은 노면의 그립은 별도 설계다. 첫 대표 장면에서는 물리 튜닝을 고정하고, 노면별 그립 변화는 이후 검증한다.

### 첫 화면 목표

**오래된 항구 창고를 개조한 피트, 비가 갠 바닥에 비치는 따뜻한 정비등, 부분적으로 젖은 아스팔트 위의 GT 한 대.**

먼저 차고 밖 피트 출구와 첫 코너 약 100~150m를 미술 집중 구역으로 만들고, 계획의 300m 시험 주행 구간 안에 배치한다. 실제 주행 카메라와 차고의 높은 3/4 카메라에서 같은 차량·재질을 검수한다. 높은 카메라에서만 잘 보이는 장면으로 통과시키지 않는다.

검수 화면은 중립 차량, 차고 3/4, 뒤에서 본 주행, 측면광 코너, 역광 주행, 모바일 저화질이다. 합격 조건은 차체/타이어 구분, 네 바퀴 접지, 반사 깜빡임·표면 겹침 없음, 코너 출구와 표지 가독성, 실제 플레이 중 프레임 안정성이다. 디테일 수보다 이 조건을 먼저 통과한다.

이번 보완은 그래픽 목표의 구체화다. 게임 장르를 탐험 RPG로 바꾸거나 원본 UI·로고·에셋을 복제하는 제안은 아니다. 첫 실제 렌더 결과에서 현재 에셋의 한계를 평가한 뒤 대표 모델 교체 범위를 결정한다.

## 16. 최신 사용자 선택: 해안 서킷과 레퍼런스 차고

### 게임의 중심은 레이싱

사용자는 스타일라이즈드 해안 서킷을 선택했고, 첨부 레퍼런스를 차고 모습으로 활용하자고 제안했다. 따라서 신규 개발 기준은 **달릴 때는 탁 트인 해안 서킷, 쉬거나 차량을 고를 때는 밀도 높은 항구 정비 차고**로 정리한다. 로봇 탐험·도시 복구·학습 요소는 포함하지 않는다.

| 구분 | 해안 서킷 | 독립 차고 |
|---|---|---|
| 역할 | 고속 주행·코너 공략·추월·기록 개선 | 차량 감상·선택·색상 확인·출전 |
| 카메라 | 후방 추적, 제동 지점과 코너 출구 시야 우선 | 높은 3/4 디오라마 기본, 제한된 궤도 회전으로 차량 확인 |
| 공간 | 긴 직선, 해안 스위퍼, 절벽 구간, 피트 | 오래된 항구 창고를 개조한 정비 작업장 한 동 |
| 빛과 재질 | 밝고 읽기 쉬운 노면·연석·차량, 배경은 절제 | 청록·회색 벽돌과 철골, 따뜻한 작업등, 부분적으로 젖은 바닥 |
| 디테일 예산 | 코너 랜드마크·피트·가까운 안전시설에 집중 | 작업대·공구·배관·케이블·타이어 랙·출입구에 집중 |

두 공간은 같은 항구 지역의 시간대·팔레트·차량 재질을 공유한다. 하지만 차고의 어두운 노출이나 물웅덩이를 서킷 전체에 복사하지 않는다. 서킷 노면별 접지 변화는 별도 주행 검증 대상이며, 차고의 젖은 표현은 미술 표현이다.

### 차고 한 장면의 구체적인 배치

- 중앙: 대표 GT 한 대를 실제 바닥 위에 놓는다. 떠 있는 회전판, 차량을 덮는 블룸, 차체를 단색으로 바꾸는 임시 보정을 기본으로 쓰지 않는다.
- 뒤쪽: 두꺼운 벽돌 벽, 철골 기둥, 높은 창, 노출 배관. 원작 성벽이나 지형을 복제하지 않고 자동차 정비소의 구조로 재해석한다.
- 왼쪽: 작업대·공구함·정비등. 가까운 디테일을 집중하되 차량 실루엣과 겹치지 않게 한다.
- 오른쪽: 타이어 랙·예비 휠·소형 압축기. 휠과 타이어가 잘 구분되도록 재질과 조도를 검수한다.
- 앞쪽: 카메라를 향한 벽/지붕을 열어 내부가 보이는 단면형 구성. 추가 방을 무작정 붙이지 않는다.
- 열린 셔터 너머: 피트 출구, 바다와 항구 크레인의 원경. 차고와 서킷이 같은 장소라는 연결감을 준다.
- 바닥: 마른 거친 콘크리트가 기본이고 출입구 근처만 젖게 한다. 배수구·타이어 자국·접지 그림자로 규모와 무게를 읽게 한다.

무료 모델을 한꺼번에 쌓는 대신 명시적인 배치 데이터로 구성한다. 대표 차량·실내 벽·작업대처럼 가까이 보이는 것부터 검수한다. 레퍼런스의 그래픽 원칙만 참고하고 로고·UI·캐릭터·원본 에셋은 가져오지 않는다.

### 차고 기능과 화면 흐름

첫 차고는 대표 차량 한 대를 제대로 보여 주는 데 집중한다. 차량명, 색상 선택, 카메라 초기화, 출전, 설정만 우선 제공한다. 차종이 추가되면 같은 공간에서 모델을 바꿔 확인한다. 검증되지 않은 파워/그립 수치, 재화·등급·해금 경제, 걸어다니는 정비사, 수리 미니게임은 첫 범위에서 제외한다.

흐름은 **차고 → 출전 → 서킷 로딩/그리드 → 주행 → 결과 → 재도전 또는 차고**다. 실제 경기 로딩 중에는 상태를 표시하고 이중 출전을 막는다. 차고 문을 통과하는 연출은 이후 선택 사항이며 초기에는 자유 주행 연결 월드를 만들지 않는다.

차고와 경기에서 같은 차량 명세·텍스처·휠 피벗을 사용한다. 조명은 공간별로 조정하되 차체 색이나 부위 판정 코드를 서로 다르게 덧붙이지 않는다. 전환 때 렌더/물리 자원을 정리하고 차량 선택·색상·설정은 유지한다.

### 수정된 첫 제작 순서

1. **차고 목표 이미지와 배치 명세:** 사용자 레퍼런스를 자동차 정비 공간으로 번역한다. 콘셉트는 실제 렌더 결과와 구분한다.
2. **작은 실제 차고 장면:** 대표 GT·작업대·벽·정비등·출입구로 재질과 비례를 검증한다. 아직 메뉴·수집 기능을 늘리지 않는다.
3. **동일 차량의 300m 주행:** 기존 계획의 고정 스텝·접지·가속/제동·추적 카메라를 검증한다. 예쁜 차고가 주행 문제 해결을 대신하지 않는다.
4. **해안 서킷 한 랩과 최소 차고 연결:** 타임어택·재시작·결과·저장까지 완성한다.
5. **미술 확장과 경쟁:** 피트/해안 디테일, AI 3대의 추월·복귀, 전체 흐름과 성능 검수 순서로 확장한다.

11절의 상세 검증 항목은 유지하지만, 독립 차고의 미술 검증을 마지막까지 미루지 않는다. 15절의 레퍼런스 밀도는 차고를 주 대상으로 삼고 서킷에서는 피트 입구 등 일부 구간에만 적용한다.

첫 제출 증거는 차고 3/4·차량 전후측면·실제 후방 주행 화면이며, 차고/주행 각각 같은 차량이 정상적으로 보이는지 비교한다. 성능은 두 공간을 따로 측정하고 차고↔경기 반복 전환도 검사한다. 이 절은 기획 변경이며 아직 콘셉트 생성·게임 구현·배포를 완료한 것은 아니다.
