# 오픈소스 차량 제어와 MUMU CIRCUIT 비교

2026-10-10 기준으로 `pmndrs/racing-game`, `pmndrs/ecctrl`, Three.js 공식 Rapier 차량 예제의 실제 제어 코드를 현재 로컬 웹 소스와 비교했다.

**우선 권장하는 방향은 기존 차량 8종과 맵을 유지하면서 차량 제어를 정리하는 것이다.** 현재 코드에는 효과가 없는 튜닝 값과 서로 다른 차체 지지 계산이 공존한다. `ecctrl`의 타이어·접지 설계를 참고할 가치가 크지만, 레포 전체 교체가 꿀렁임 해결을 보장하지는 않는다. 차체 흔들림의 정확한 재현 구간은 아직 특정되지 않았다.

## 비교 대상과 적용 범위

| 대상 | 실제 구성 | 우리 프로젝트에 필요한 부분 | 그대로 도입할 때의 비용 |
| --- | --- | --- | --- |
| MUMU CIRCUIT | Three.js 직접 렌더링 + Rapier 0.20 + React UI | 기존 8종 모델, 바퀴 리그, 공유 물리 월드, 레이스·입력·VFX | 현재 기반 |
| pmndrs/racing-game | React Three Fiber + Cannon raycast 차량 | 가속·조향·음향·이펙트를 연결하는 흐름 | 물리 엔진과 렌더 구조 전환 필요; 진동 연출도 포함 |
| pmndrs/ecctrl | React Three Fiber + Rapier, 사용자 정의 shape-cast 타이어 | 접점 안정화, 바퀴 토크·미끄러짐 곡선, 구동 배분 | R3F 구조와 새 타이어 해석기 통합 필요 |
| Three.js 공식 차량 예제 | Three.js + Rapier 기본 차량 컨트롤러 | 바퀴 포즈와 API 사용 비교 | 상자 차량·평면 바닥의 예제라 레이스 기능과 튜닝은 별도 |

`racing-game`의 의존성은 Three ^0.139, React ^18, Cannon ^6.3이다. `ecctrl` 분석본은 2.0.2이고 R3F >=9.4, react-three-rapier >=2.2, React >=19.2.7을 요구한다. 우리 설치본 React는 19.2.7이지만 R3F·react-three-rapier는 사용하지 않는다. 따라서 `ecctrl`은 설치만으로 기존 `runtime.js`에 붙는 모듈이 아니다. [racing-game package](https://github.com/pmndrs/racing-game/blob/7816a5d954b75e6ad853ae4e4f0cbbd628072643/package.json) · [ecctrl package](https://github.com/pmndrs/ecctrl/blob/e2cab804f9f15661a642e76f52d09f0b2db63f35/package.json)

## 현재 코드에서 확인된 문제

### 1 차체 지지 계산이 두 단계로 나뉜다

현재 순서는 다음과 같다.

1. [physics.js](../src/driving/physics.js)에서 Rapier `updateVehicle(STEP)`가 서스펜션·타이어에 따른 차체 속도를 계산한다.
2. [activeRide.js](../src/rebuild/activeRide.js)에서 접지 바퀴가 3개 이상이면 피치·롤 회전을 잠그고 도로 법선에 맞춰 회전을 직접 지정한다.
3. 이어서 도로 접점 평균으로 목표 높이를 만들고 수직 속도를 다시 지정한다.
4. 공유 `world.step()`으로 충돌과 중력을 적분한다.

즉 차체의 최종 수직 속도는 Rapier 서스펜션 결과를 그대로 쓰지 않는다. 안정화가 작동하는 동안 차체 감쇠·안티롤·다운포스 분기도 건너뛴다. 안정화 의도 자체는 사용자가 요청한 흔들림 제거와 맞지만, 어느 계산이 차체 지지를 책임지는지 명확하게 정리할 필요가 있다.

**꿀렁임 원인 후보:** 바퀴 접지가 3개에서 2개로 바뀌거나 도로·연석·지형의 접점이 바뀌면 안정화의 잠금과 해제가 전환된다. 법선 방향은 평활화하지만 높이 계산은 그 순간의 접점 평균을 사용한다. 도로 경계에서 목표 높이·수직 속도·차체 각도가 급하게 달라질 가능성이 있다. 이 경로가 사용자가 느낀 증상의 원인인지는 실제 구간 계측이 필요하다. `activeRide`를 무작정 끄면 이전 서스펜션 흔들림이 돌아올 수 있다.

### 2 네 가지 튜닝 값을 바꿔도 현재 주행에 반영되지 않는다

| 설정 | 코드의 실제 동작 | 이번 비교 실험 |
| --- | --- | --- |
| `grip` | 차량별 값 대신 타이어 계산에 2.3을 직접 사용 | 2.3 → 0.4, 결과 동일 |
| `antiRoll` | `!activeRide`일 때만 적용; 현재 8종 모두 activeRide 켬 | 6500 → 0, 결과 동일 |
| `bodyDamping` | 같은 조건에서만 적용 | 5 → 50, 결과 동일 |
| `aero` | 같은 조건에서만 적용 | 0.55 → 50, 결과 동일 |

수프라를 별도 임시 물리 월드에서 평면 바닥에 2초 정착시킨 뒤, 6초 동안 가속과 작은 사인파 조향을 적용했다. 각 설정을 하나씩 바꾼 4개 실험에서 위치·회전·속도·바퀴 하중 **720개 표본 전체가 기준 주행과 정확히 같았다**. 관측 범위는 이 통제된 실험이다. 실제 전체 코스 증상을 재현한 결과는 아니다. [실험 코드](../artifacts/repository-analysis-20261010/inspect.mjs) · [결과 JSON](../artifacts/repository-analysis-20261010/probe.json)

### 3 차량별 외형 차이보다 주행 차이가 작다

질량·토크·기어비·휠베이스·반지름에는 차이가 있다. 하지만 현재 레이스는 8종 모두 뒷바퀴에 절반씩 구동력을 배분한다. GT-R도 현재 구현에서는 후륜구동이다. 기본 타이어 계수와 최고속도 한도도 공통이다. [차량 설정](../src/rebuild/vehicleDynamics.js) · [구동 배분](../src/driving/physics.js)

엔진 RPM은 차체 전진 속도와 바퀴 반지름으로 추정한다. 타이어가 헛돌거나 잠기는 회전 상태가 엔진 RPM·토크에 직접 되먹임되는 구조는 아니다. 그래서 정교한 번아웃·브레이크 잠김·구동 방식의 차이를 표현하는 데 한계가 있다. 이 사실이 자동으로 꿀렁임의 원인을 의미하지는 않는다.

### 4 고속 조향과 카메라가 매우 억제돼 있다

수프라의 현재 최대 중앙 조향각은 아래와 같다. 실제 좌우 바퀴 각도는 Ackermann 계산으로 조금씩 달라진다.

| 속도 | 중앙 조향각 한도 |
| --- | --- |
| 60 km/h | 9.05° |
| 120 km/h | 2.10° |
| 180 km/h | 0.77° |
| 240 km/h | 0.41° |

고속에서 조향각을 줄이는 것은 타당하다. 다만 현재 곡선이 실제 코스에서 원하는 코너 반응을 주는지는 별도 문제다. 곧바로 각도를 키우면 과도한 회전과 미끄러짐이 생길 수 있으므로 속도별 선회 반경과 사람의 체감을 함께 비교해야 한다. [steering.js](../src/driving/steering.js)

현재 레이스는 `stableRide:true`를 전달한다. 이 모드에서 카메라의 가속·제동에 따른 앞뒤 움직임과 충돌 흔들림은 비활성화된다. 속도에 따른 FOV 변화도 기본 54°에서 최대 약57°다. 시야 안정성에는 도움이 되지만 가속·제동 느낌이 약해지는 후보다. 원하는 안정성을 유지하면서 음향·노면·속도 표현부터 개선하는 편이 안전하다. [카메라](../src/driving/chaseCamera.js) · [레이스 호출부](../src/rebuild/runtime.js)

### 5 긴 프레임에서 시간이 버려진다

물리 업데이트는 1/120초 고정 간격이고, 여섯 차량을 갱신한 뒤 월드를 한 번 적분한다. 렌더링에는 이전·현재 포즈 보간도 있다. 이 구조는 유지할 가치가 있다.

다만 렌더 루프가 프레임 간격을 최대0.05초로 제한한다. 100ms가 걸린 프레임에서는 50ms만 시뮬레이션에 전달된다. 긴 프레임이 반복되면 실제 시간에 비해 주행이 느려진다. 프레임 제한은 과도한 따라잡기 계산을 막지만, 누락 시간과 물리 비용을 관측하지 않으면 끊김과 물리 흔들림을 혼동하기 쉽다. [runtime.js](../src/rebuild/runtime.js)

## 레포에서 참고할 설계

### ecctrl의 접점과 타이어 계산

타이어 부피를 내려 보내 바닥을 찾는 shape cast와 일반 ray cast를 선택할 수 있다. 접촉 위치를 바퀴 중앙 단면으로 보정하고, 지지 힘과 마찰 힘을 서로 다른 지점에 적용한다. 바퀴 회전속도·접점 속도 차이로 미끄러짐을 계산하고, 하중과 곡선으로 허용 마찰을 제한한다. 구동 바퀴별 가중치도 있다. **우리에게 가장 유용한 참고 대상은 이 접점·타이어 계층이다.** [ShapeCastWheel](https://github.com/pmndrs/ecctrl/blob/e2cab804f9f15661a642e76f52d09f0b2db63f35/src/vehicles/components/ShapeCastWheel.tsx#L537) · [지지·마찰 적용](https://github.com/pmndrs/ecctrl/blob/e2cab804f9f15661a642e76f52d09f0b2db63f35/src/vehicles/EcctrlVehicle.tsx#L511)

그대로 가져오기에는 제약도 있다. 차량과 바퀴 계산이 `useFrame`에 연결되고 힘 적분에는 `world.timestep`을 사용한다. 렌더 프레임 수와 실제 물리 서브스텝 수가 다를 때 같은 응답을 보장하는지 별도로 검증해야 한다. 우리 구현에 적용한다면 계산은 120Hz 물리 단계, 보이는 포즈는 렌더 단계에 배치하는 것이 권장된다. 새 shape cast의 여섯 차량 비용도 측정해야 한다. [wheel loop](https://github.com/pmndrs/ecctrl/blob/e2cab804f9f15661a642e76f52d09f0b2db63f35/src/vehicles/components/ShapeCastWheel.tsx#L910) · [vehicle loop](https://github.com/pmndrs/ecctrl/blob/e2cab804f9f15661a642e76f52d09f0b2db63f35/src/vehicles/EcctrlVehicle.tsx#L806)

### racing-game의 연결된 주행 연출

가속·조향·브레이크와 카메라·차체·소리를 연결한다. 다만 차체와 카메라에 주기적인 진동도 직접 넣는다. 현재 사용자의 흔들림 제거 요구에 이 진동을 가져오면 맞지 않는다. 입력 보간은 `delta * rate`, 부스트 소비는 프레임당1이라 우리 시간 기반 처리를 대체할 이유도 약하다. [Vehicle](https://github.com/pmndrs/racing-game/blob/7816a5d954b75e6ad853ae4e4f0cbbd628072643/src/models/vehicle/Vehicle.tsx#L54)

먼지는 미끄러짐·브레이크 상태와 속도를 이용하며, 스키드 자국은 브레이크와 속도로 생성한다. 우리 구현은 이미 바퀴 접점·법선·미끄러짐 신호를 사용하므로 기능 자체를 다시 가져올 필요는 작다. 타이어가 왜 미끄러졌는지와 이펙트 발생 신호가 일치하는지를 개선하는 편이 좋다. [Dust](https://github.com/pmndrs/racing-game/blob/7816a5d954b75e6ad853ae4e4f0cbbd628072643/src/effects/Dust.tsx) · [Skid](https://github.com/pmndrs/racing-game/blob/7816a5d954b75e6ad853ae4e4f0cbbd628072643/src/effects/Skid.tsx) · [우리 신호](../src/driving/drivingSignals.js)

### Three.js 공식 예제의 역할

기본 컨트롤러와 바퀴 포즈 연결의 기준으로 유용하다. 하지만 10kg 상자 차량과 평면 바닥이며, 제어 업데이트는 렌더마다 `1/60`으로 호출한다. 물리 헬퍼는 별도의 interval에서 실제 시간 간격으로 월드를 갱신한다. 물리·렌더 단계가 하나의 고정 루프로 묶인 완성형 레이싱 구현은 아니다. 예제의 마찰·서스펜션 숫자를 우리 1.3~1.7t 차량에 그대로 적용하지 않는다. [차량 예제](https://github.com/mrdoob/three.js/blob/5d8e8a89347650ee210e120cdd70f9e9288f0abc/examples/physics_rapier_vehicle_controller.html#L328) · [물리 헬퍼](https://github.com/mrdoob/three.js/blob/5d8e8a89347650ee210e120cdd70f9e9288f0abc/examples/jsm/physics/RapierPhysics.js#L302)

## 우리 코드에서 유지할 부분

- 공유 월드의 120Hz 물리 처리와 포즈 보간. 카메라는 속도가 높아져도 월드 위치를 뒤늦게 따라가는 방식이 아니다.
- Blender 바퀴 리그의 서스펜션·조향·회전 분리. 현재 바퀴는 Rapier 상태를 읽어 움직인다. [assets.js](../src/rebuild/assets.js)
- 차 대 차 차체 충돌과 타이어 지면 검사의 분리. 다른 차량을 타이어의 바닥으로 취급하지 않는다.
- 실제 도로 trimesh와 `FIX_INTERNAL_EDGES`. 삼각형 경계 보정은 이미 있으므로 미구현으로 진단하지 않는다. [worldCollision.js](../src/rebuild/worldCollision.js)
- 접점 기반 스키드 자국, 입자 수 제한, 입력 해제와 충돌·복귀 회귀 검사.

`controller.setIndexForwardAxis = 2`도 문법 오류가 아니다. 설치된 Rapier 0.20 타입에서 이 이름은 setter 속성으로 정의되며, 이번 임시 시뮬레이션에서 forward axis 값2를 확인했다.

## 권장하는 다음 구현 순서

1. **한 대·실제 문제 구간을 계측한다.** 수프라에서 차체 높이·각도, 접지 수, 바퀴별 접점·법선·하중, 안정화 잠금 상태, 카메라 포즈, 원래 프레임 시간과 누락 시간을 동시에 기록한다. 완전 평면·도로 연결부·연석·잔디 복귀·경사 변화·충돌을 구분한다.
2. **차체 지지 책임을 정리한다.** 현재 안정화와 타이어 계산이 만나는 지점에서 불연속이 생기는지 먼저 확인한다. 접지 전환·도로 법선 변화의 연속성을 개선하고, 실제 점프·충돌 반응은 보존한다. 흔들림 제거를 가짜 차체 애니메이션으로 되돌리지 않는다.
3. **효과가 있는 차량 설정만 연결한다.** grip·앞뒤 구동 배분·브레이크 배분·조향 곡선을 검증한다. 안티롤·다운포스는 새 차체 지지 방식과 충돌하지 않는 경우에만 활성화한다. 설정 변경이 실제 선회·제동 결과를 바꾸는 회귀 검사를 둔다.
4. **타이어 모델 도입은 별도 A/B로 비교한다.** 기본 Rapier 컨트롤러 정리본과 ecctrl의 접점·미끄러짐 설계를 참고한 시험본을 같은 수프라·구간·입력·속도에서 비교한다. 후자가 체감과 안정성에서 이득일 때 나머지7종에 확장한다.
5. **안정된 상태에서 운전 느낌을 다듬는다.** 조향 반응, 미끄러짐 진입·회복, 타이어 소리와 연기, 기어 변속음을 함께 맞춘다. 카메라 진동 없이도 가속과 제동을 읽을 수 있게 한다. 6대·30/60/120FPS 조건과 실제 휴대폰 성능을 확인한다.

최종 목표는 단순히 차체 회전이0인 것이 아니라, 반복 흔들림 없이 원하는 선회·제동·접촉 결과가 나오고 바퀴와 이펙트가 그 결과를 보여주는 것이다. 평면 정착·충돌·복귀 기존 검사를 유지하면서 실제 도로의 높이 변화와 접지 전환을 추가해야 한다. 현재 평면 및 일정 경사 시험만으로 사용자의 전체 코스 꿀렁임이 해결됐다고 판단하지 않는다. [현재 검사](../scripts/fleet-eight.test.mjs) · [카메라·평면 검사](../scripts/ride-quality.test.mjs)
