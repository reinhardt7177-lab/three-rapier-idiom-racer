# 온라인 1:1 설계 검토·임시 사본 정리

2026-10-15 · 작업 브랜치 `codex/korea-circuits-progression-20261011`

## 판정과 범위

현재 모드는 **초대 링크/방 코드로 연결하는 친구 대전**이다. 임의의 상대를 찾는 공개 매칭 대기열, 순위 서버, 호스트의 부정행위를 막는 서버는 없다. 방장이 두 차량의 실제 Rapier 물리와 결승 판정을 계산하고 참가자는 입력만 보낸다. 이 구조는 두 사람의 충돌·시간 판정을 한 세계에서 유지하지만 참가자의 입력에는 왕복 지연이 발생하며 방장의 창과 계산 능력에 의존한다.

사용자는 이번 요청에서 검증 뒤 배포와 임시 사본 삭제를 승인했다. main 커밋·병합·PR 생성, DNS/보안 설정 변경, Colab 자동 활용은 범위에 없다. 기존 조향·AI·남악·차량 작업을 보존하고 함께 검사한다. 이번 온라인 수정에서 차량 물리·기록 기준·도로는 바꾸지 않았다.

## 발견과 수정

프로토콜은 v2다. 기존 v1 창과는 연결을 거절하며 두 사람에게 새로고침을 안내한다. 공개 PeerServer는 연결 중개용이며 실제 경기는 WebRTC 데이터 채널이다. 연결된 데이터 채널이 살아 있으면 중개 소켓 장애만으로 경기를 끊지 않는 기존 동작을 유지했다.

## 실제 검증

- 수정 전 관련 19/19 통과. 기존 시험만으로 위 실패 경로를 검증하지 못했다.
- 최종 관련 **30/30 통과**. 새 시험 11개는 참가 확인/준비 시간 초과, 오류·거절된 Promise, 혼잡 제어, 재경기 메시지, 조기 go, 정지·순서, 설정, 8초 감시, 늦은 peer를 확인한다. 가상 타이머는 실제 상수를 사용하며 기준을 줄이지 않았다.
- 늦은 peer 회귀 시험은 수정 전 `hosting !== error`로 실패했다. 원래 실패 로그를 보존했고 수정 후 통과했다.
- 실제 IAB 두 창/PeerServer/WebRTC, 남악 맑음 1랩, 수프라/GT-R의 공개 UI 완주 기록은 **76.13초/80.32초**, 양쪽 시간·승패 일치. 같은 방 대기실 복귀·두 준비 초기화·재경기·공유 정지/재개를 확인했다. 재경기 약40.79초에 참가자 창 종료 후 방장이 중단되고 재개 버튼이 비활성화되며 허위 완주가 생기지 않았다.
- 위 완주 이후 마지막 늦은 연결 정리 수정을 추가했다. 이 최종 소스의 추가 실제 검수와 전체 검사 결과는 아래에 별도로 기록한다.
- 참가자 대기실 4크기(1280×720, 1024×768, 844×390, 667×375) 실제 viewport 일치·버튼/입력 잘림·겹침 0. 결과 화면도 네 실제 크기에서 패배 제목을 확인한 뒤 카드·버튼 잘림 0. 휴대폰 실기기 검증이 아니다.
- 최초 크기 검사는 방장 창이 계속1280인 표본을 잘못 측정했다. 버리고 숨기지 않고 `lobby-layouts-wrong-tab.json`에 분리했다. 결과 크기 변경은 의도된 공유 정지를 유발했다. 첫 결과라고 이름 붙인 캡처는 정지 메뉴 표본이며, 재개 후 제목까지 확인한 `result-layouts-corrected.json`·`result-visible-*`가 올바른 근거다.
- 방장 콘솔은 실행 오류 0, Three/D3D 셰이더 수치 정밀도 경고 1이었다.

계산은 로컬 Windows CPU/Rapier WASM이다. Colab·원격 GPU를 사용하지 않았다. 최종 연결 정리 수정 이전에 시작한 첫 전체 검사는 757.97초 시점에 명시적으로 중단해 재실행했다. 그 실행은 전체 통과 근거가 아니며 로그와 변경된 입력2개를 기록했다.

## 임시 사본 정리

일반 파일 삭제 합계 **4,365개·2,280,198,653바이트(약2.28GB/2.12GiB)**. 중복 계산 없이 첫 tar 210,688,000B + 1차2,879파일/1,487,102,343B + 2차1,485파일/582,408,310B다. 검증용 소스/모델 tar, 과거 baseline/검증 빌드/배포 복제본, 변경 전 복제 파일을 정리했다. 실제 원본 `src/public/assets-sources`·의존성·Git 이력과 현재 코드에서 참조하는 재생성 자료, 실패 로그/사진/단위 시험 fixture는 보존했다.

최초 `validation-source/node_modules` 연결 제거는 자동 승인 검토가 `blocked by policy`로 거부했다. 상세 사유는 제공되지 않았다. 이후 연결을 제거하거나 따라가지 않는 **일반 파일만의 더 좁은 삭제**로 진행했다. 각 파일의 절대 경로·부모 경로의 reparse 여부·크기·수정 시각을 검사하고 `Remove-Item -LiteralPath`로 개별 삭제했다. 삭제 때 재귀 옵션은 쓰지 않았다. 2차 목록에는 크기0인 연결14개가 남아 있으며 실제 의존성/공개 에셋을 가리키는 연결은 삭제하지 않았다. 이 항목의 정리까지 완료했다고 주장하지 않는다.

이미 지운 검증 빌드를 제공하던 과거 preview 서버5개를 종료했고 주 개발 서버5191은 유지했다. 삭제 목록·용량과 보존 항목은 `artifacts/online-review-20261015/cleanup-regular-result-first.json`, `cleanup-regular-result.json`, `cleanup-regular-plan*.json`에 있다. 오래된 문서의 before/임시 preview 링크는 삭제된 복제본을 가리킬 수 있으며 현재 자료 위치와 구분한다.

배포 뒤 이번 작업의 before4파일·검수 HTML/모니터2파일을 마감 정리하려던 별도 명령도 자동 승인 검토가 거부했다(상세 사유 없음). 이6파일도 삭제하지 않았고 다른 도구로 우회하지 않았다. `cleanup-final-blocked.json`에 기록했다. 따라서 **4,365개를 삭제했지만 모든 연결/이번 임시 검수 사본까지 삭제 완료라고 주장하지 않는다.**

## 미검증과 출시 한계

1. 서로 다른 실제 기기·통신망, 강한 NAT/회사망, 장시간 고지연/패킷 손실 운전은 미검증이다. 같은 PC 두 창의 성공을 이 범위로 확대하지 않는다.
2. 과거 문서의 ‘TURN 없음’은 현재 설치된 PeerJS1.5.5 번들과 맞지 않는다. 실제 번들 기본 설정에는 Google STUN과 PeerJS 공유 TURN 주소가 있다. **이 게임이 관리하는 전용 TURN·서비스 보장은 없다.** 공유 relay의 실제 사용·가용성은 이번에 검증하지 않았다.
3. 호스트 신뢰 구조와 입력 지연은 친구 대전의 한계다. 경쟁 순위/상금 대전 수준의 공정성을 보장하지 않는다. 중도 이탈은 승리로 처리하지 않는다.
4. 두 탭과 무거운 로컬 회귀를 동시에 실행한 화면 검수는 성능 비교가 아니다. 앞 차량 작업의 남악 A/B/A는 원본 자체의 p95 변동으로 미결론이며 이번에 통과로 바꾸지 않는다.

- [PeerJS 공식 소스](https://github.com/peers/peerjs): 설치 번들의 ICE 설정과 공개 문서 기본값은 차이가 있어 번들도 확인했다.
- [Vercel 배포 API](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment): 기존 프로젝트/브랜치의 정확한 검증 커밋 배포.

다음 우선순위는 두 실제 기기·서로 다른 통신망의 초대 대전과 지연 체감 검수다. 자동 무작위 매칭은 별도 제품 범위로 결정해야 한다.
