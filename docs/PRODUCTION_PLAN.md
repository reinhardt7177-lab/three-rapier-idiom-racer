# MUMU CIRCUIT — 해안 서킷 · 항구 차고 제작 실행안

작성일: 2026-09-05  
상태: 초기 제작 계획 + 후속 실행 갱신 (본문의 구현 전 설명은 초기 시점 기록)  
최신 방향: [레이싱 체감·연출 작업 계획](DRIVING_EXPERIENCE_PLAN.md)을 다음 주행 작업 기준으로 삼는다. 레퍼런스의 협곡 외형이 아니라 코너·드리프트·탈출 가속의 피드백을 참고하며 항구/해안 미술은 유지한다. 다음 구현은 계측 + 코너 시험 구간이다.  
현재 구현: 자체 코드 GT/차고, Rapier 120Hz 주행 시험장, 추격 지연을 제거한 카메라, 노면/도로변 디테일, 선택형 합성 주행음, 자동 시험 14개. [차량 1단계](VEHICLE_STAGE1.md)와 [속도감 2단계](SPEED_FEEL_STAGE2.md)가 실제 구현 기준이다. 아래 초기 기능/에셋/물리 스텝 제안과 충돌하면 후속 기록을 우선한다.  
실행 갱신: 후속 사용자 요청에 따라 외부 에셋을 사용하지 않는 소규모 차고 시안을 구현했다. 상세는 [첫 시안 기록](GARAGE_PROTOTYPE.md). 아래 본문은 전체 게임 제작 계획이며, 전체 단계 완료를 뜻하지 않는다. 에셋 선별 제안은 현재 자체 코드 제작 방향으로 변경됐다.
차고 2차 갱신: 사용자가 첫 시안의 분위기를 유지한 발전을 요청해 [차고 발전 계획](GARAGE_EVOLUTION.md)에 따라 항구 연결·셔터·환경 저장·포토 모드를 구현했다. 실제 레이스는 여전히 후속 단계다.
현재 개발 기준 문서. RACING_REBUILD_PLAN.md의 코드 분석은 과거 이력으로, 16절의 장르 선택은 본 문서의 출발점으로 유지한다.

## 1. 결론과 약속 범위

**스타일라이즈드 해안 레이싱을 만들고, 사용자가 제시한 AFTERLIGHT 이미지의 재질·명암·공간 밀도를 독립 항구 차고의 미술 기준으로 삼는다.**

레퍼런스와 비슷한 인상을 내는 데 필요한 재질과 그림자 표현은 현재 렌더링 기반에서 구현 후보로 삼을 수 있다. 하지만 원본과 동일한 결과·제작 시간·모든 기기의 60FPS를 보장하지 않는다. 작은 실제 차고 장면을 제작해 화면과 성능을 함께 검증한 뒤 품질 범위를 확정한다.

원작 캡처에서 확인한 것은 높은 사선 카메라, 두꺼운 벽돌 구조, 부분적으로 젖은 바닥, 긴 그림자, 따뜻한 실내등, 제한된 색상이다. 원본의 소스·에셋 라이선스·렌더링 기법은 확인하지 않았다. 참고하는 것은 미술 원칙이며 원작 맵·로고·UI·캐릭터를 복제하지 않는다.

현재 src에는 재구축 안내 화면만 있다. 차량·주행·차고·검사 로직은 사용자 요청으로 제거했고, ZIP 백업과 Git 이력·기획서·에셋은 보존했다. 지금의 npm run check는 빌드만 검사한다. 아래 모든 기능과 수치는 제작 목표이지 현재 구현 결과가 아니다.

## 2. 첫 완성본의 범위

- 차고 한 동: 차량 감상, 색상 선택, 카메라 초기화, 출전, 설정.
- 대표 GT 한 대: 동일 외형·재질·바퀴 명세를 차고와 레이스에서 공유.
- 해안 서킷 한 개: 타임어택, 체크포인트, 기록 저장, 즉시 재시작.
- 그 다음 경쟁 단계: 같은 물리 규칙의 AI 세 대, 3랩 레이스.
- 제외: 학습, 탐험/복구 게임, 오픈월드, 온라인 멀티플레이, 차량 40종, 재화·해금 경제, 수리 미니게임, 날씨/낮밤 실시간 순환.

완료 경험은 **차고에서 차를 보고 → 바로 출전 → 코너를 익혀 기록 개선 → 재도전 또는 차고 복귀**다. 미술과 손맛을 확인하기 전 기능 수를 늘리지 않는다.

## 3. 차고 미술 명세

### 목표 한 장면

비가 그친 늦은 오후, 항구 창고를 개조한 작은 정비소. 열린 셔터로 햇빛이 비스듬히 들어오고, 출입구의 젖은 콘크리트에 작업등 빛이 번진다. 중앙의 GT는 차체·유리·타이어가 분명히 구분되며 네 바퀴로 바닥을 딛고 있다. 셔터 밖에는 피트와 바다가 보인다.

초기 배치 기준은 실내 약 14m × 11m, 높이 약 5m다. 최종 규격은 차의 실측 크기와 카메라 검수 후 조정한다. 주인공을 크게 보이게 하려고 자동차를 건물만큼 키우지 않는다.

| 구역 | 주요 배치 | 미술상 역할 |
|---|---|---|
| 중앙 정비 베이 | GT 1대, 바닥 구획선, 배수구 | 가장 밝고 읽기 쉬운 주인공 영역 |
| 왼쪽 벽 | 작업대, 공구함, 정비등, 케이블 | 따뜻한 생활감과 근거리 디테일 |
| 오른쪽 벽 | 타이어 랙, 예비 휠, 압축기 | 차량 크기 비교, 재질 차이 |
| 뒤쪽 | 두꺼운 벽돌, 높은 창, 철골·배관 | 레퍼런스의 입체감과 깊이 |
| 셔터 입구 | 부분적인 물기, 턱, 외부 피트 | 안과 밖의 명암 대비 |
| 원경 | 바다, 방파제, 크레인 실루엣 | 서킷과 같은 항구라는 연결감 |

카메라 쪽 벽/지붕은 내부가 보이는 단면형 구조로 만든다. 기본은 높은 3/4 시점이며 차량 회전 보기용 카메라에 제한된 범위만 허용한다. 벽을 관통하거나 차량이 프레임 밖으로 사라지는 자유 회전은 제공하지 않는다.

### 품질을 만드는 다섯 층

1. 형태: 벽 두께, 창틀 깊이, 철골 단면, 작은 모서리 굴곡을 실제 형태로 만든다. 원경에는 같은 비용을 쓰지 않는다.
2. 재질: 고무·유리·도장·금속·벽돌·콘크리트의 거칠기를 구분한다. 색상 변경은 차체로 지정된 부위에만 적용한다.
3. 조명: 낮은 햇빛 하나를 주광으로 삼고, 주변광과 소수의 작업등으로 차체 암부를 살린다.
4. 접지: 바퀴 아래 그림자, 벽 틈과 모서리의 부드러운 어두움으로 무게를 표현한다.
5. 마감: 제한된 먼지·타이어 자국·물기·식물을 넣는다. 입자·안개·블룸으로 모델 문제를 가리지 않는다.

Three.js의 [MeshStandardMaterial](https://threejs.org/docs/pages/MeshStandardMaterial.html)은 금속성·거칠기, 노멀, AO, 환경맵 기반 재질을 지원한다. 색 텍스처와 거칠기/노멀 데이터는 색 공간을 구분한다. 노멀맵은 조명 반응을 바꾸지만 외곽선의 실제 두께를 만들어 주지는 않으므로 가까운 벽과 창틀은 모델링이 필요하다.

그림자를 만드는 조명은 추가 렌더 비용이 있으므로 처음부터 모든 작업등에 그림자를 켜지 않는다. 기본 주광 그림자와 정적 음영을 우선 구성한다. [Three.js 그림자 설명](https://threejs.org/manual/en/shadows.html)

환경맵은 주변 반사 인상을 제공하지만 움직이는 자동차의 정확한 바닥 반사를 자동 생성하지 않는다. 정확한 반사가 필요하면 차고 바닥의 제한된 영역에서 별도 기법을 시험한다. 효과를 꺼도 형태와 색이 성립해야 한다.

## 4. 에셋 조달·제작 결정

로컬에는 public/assets/kenney 아래 cars, retro-urban, roads, toy 및 일부 개별 GLB/텍스처가 남아 있다. 이는 파일 존재 확인이며, 새 차고에서 모델·재질이 합격했다는 뜻이 아니다. Retro Urban Kit의 공식 라이선스 표기는 CC0다. 파일별 원본 출처는 로컬 라이선스와 함께 재확인한다. [Kenney 공식 페이지](https://kenney.nl/assets/retro-urban-kit)

| 대상 | 시작 방법 | 부족할 때의 결정 |
|---|---|---|
| 대표 GT | 기존 차량 중 후보를 중립 조명으로 전후측면 비교 | 가까운 화면에서 형태가 부족하면 별도 차체 제작. 광원/블룸으로 감추지 않음 |
| 차고 벽·셔터·철골 | 규격화된 자체 모듈과 선별한 도시 부품 조합 | 가까운 모서리·창틀·배관은 추가 모델링 |
| 타이어·공구함·표지·장비 | 기존 무료 에셋에서 실제 필요한 항목만 선별 | 없는 소품은 단순한 독립 모델부터 제작 |
| 바닥·벽 재질 | 라이선스 확인된 텍스처 또는 자체 제작 맵 | 팔레트/거칠기/스케일을 차고에 맞춰 통일 |
| 서킷 노면 | 폭·곡률·고도를 가진 자체 트랙 데이터에서 생성 | 외부 도로 모듈을 강제로 이어 붙이지 않음 |
| 원경 건물·크레인 | 낮은 비용의 선별 모델·실루엣 | 실제 카메라에서 필요한 만큼만 추가 |

대표 차량은 원래 비례를 유지하면서 미터 단위로 변환한다. 모델의 길이만 맞추고 모든 바퀴를 동일 좌표에 붙이지 않는다. 차량 명세에 앞 방향, 바퀴 중심/반경/회전축, 차체 충돌 크기, 질량과 무게중심, 재질 부위를 함께 기록한다.

모델별 파일 경로·라이선스·원본 크기·변환·재질 슬롯·텍스처를 asset-manifest에 남기고, import 실패를 조용히 빈 모델로 바꾸지 않는다. 사용자 지정이 없는 유료 에셋 구매나 계정 가입은 하지 않는다.

## 5. 단계별 작업과 납품물

기간은 에셋 검수와 목표 기기 측정 전에는 확정하지 않는다. 각 단계를 하나의 확인 가능한 결과물로 마무리하고, 기준을 넘지 못하면 확장 대신 그 원인을 수정한다.

| 단계 | 구현 작업 | 사용자에게 보여 줄 결과 | 통과 조건 |
|---|---|---|---|
| A. 화면 기준 | 차고 콘셉트 1안, 배치와 색 명세, GT 후보 검수 | 목표 이미지 + 후보 차 전후측면 | 차고가 정비 공간으로 읽히고 선택한 차의 형태가 적합 |
| B. 실제 차고 | 새 렌더 루프, 로딩/정리, 벽·바닥·GT·조명·카메라 | 로컬 3D 차고와 같은 구도의 콘셉트/실제 화면 | 재질·접지·시야 검수, 실측 성능 기록 |
| C. 주행 시험장 | 동일 GT, 고정 스텝 Rapier, 300m 직선/코너, 입력/리셋 | 직접 운전하는 데모 + 가속·제동 기록 | 앞뒤·바퀴·조향 정상, 실제 200km/h 이상 도달 가능한지 측정 |
| D. 해안 한 랩 | 전체 트랙과 충돌, 체크포인트, 타임어택, 재시작 | 한 랩 플레이 영상 + 결과/기록 | 완주·역주행·지름길·복귀 검증 |
| E. 게임 흐름 | 차고 UI, 출전/로딩/결과/저장, 효과음, 고스트 | 차고부터 경기 후 복귀까지 실행 | 전환·설정 유지·오류 복구·기록 버전 검증 |
| F. 경쟁/마무리 | AI 3대, 추월·브레이크·복귀, 서킷 미술, 저사양 옵션 | 3랩 레이스 + 품질 보고서 | 반복 레이스 안정성·성능·입력 검증 |

첫 단계의 콘셉트 이미지는 계획된 산출물이며 아직 생성하지 않았다. 생성 이미지를 로컬 게임 스크린샷처럼 제출하지 않는다. B 이후에는 실제 화면 캡처가 필수다. 검사 도구가 실패하면 빌드 성공으로 시각 검증을 대신하지 않는다.

## 6. 주행과 서킷 명세

### 차량 물리

1단위=1m로 통일한다. Rapier 동적 차체와 레이캐스트 휠을 출발점으로 삼되, 차량 컨트롤러 도입만으로 접지·드리프트가 완성됐다고 보지 않는다. 설치된 버전의 API와 휠 방향을 최소 시험장에서 검증한다. [Rapier 차량 컨트롤러 API](https://rapier.rs/javascript3d/classes/DynamicRayCastVehicleController.html)

- 물리 1/60초 고정 스텝, 누적 시간과 렌더 보간 분리. 긴 정지/탭 복귀에서는 일시정지 정책으로 큰 시간 도약을 막는다.
- 실제 이동 속도로 속도계를 계산한다. 목표 최고속은 기본 GT 기준 220km/h이며 가속/제동 거리는 측정해 조정한다. 표시 숫자만 늘리지 않는다.
- 가속·브레이크·후진·조향·핸드브레이크를 분리하고 고속 조향량은 줄인다. 드리프트는 뒤쪽 횡접지 감소와 회복을 튜닝한다.
- 엔진/제동·횡그립·안정 보정의 책임을 분리한다. 매 프레임 속도나 위치를 강제로 덮어써 충돌을 무효화하는 중첩 보정은 기본 구조로 쓰지 않는다.
- 연석·배리어·차량 충돌, 차체 CCD, 경사와 노면 이음매를 시험한다. 바퀴 회전은 시간·반경·후진 부호에 맞춘다.
- 경기 코드에서 실제 사용하는 컨트롤러를 자동 시험에도 사용한다. 시험 전용 가속식을 복제하지 않는다.

### 코스 제안: COASTLINE GP

전체 약 1.8km, 도로 폭 기본 16m를 초기 설계값으로 한다. 좁은 구간 약 14m, 추월 구간 18~20m는 주행 검수 후 조정한다. 코너 수나 폭을 먼저 고정하지 않고 자동차 비례·시야·제동 거리를 함께 확인한다.

구간 흐름: **600m 피트 직선 → 200m 제동/첫 코너 → 300m 해안 스위퍼 → 250m 상승 S구간 → 150m 능선 연결 → 300m 최종 코너**. 길이는 각 구간의 주행 경로를 합친 제안값이며 아직 만들어진 트랙은 아니다.

피트 직선에서는 200km/h 이상을 체감하고, 첫 코너에서 제동·탈출을 배우며, 바닷가 곡선과 높낮이에서 코스의 차이를 느끼게 한다. 목표 한 랩 60~90초는 완성 후 측정한다. 고속 구간의 점프나 막힌 블라인드 코너는 첫 코스에서 제외한다.

트랙 명세에는 중심 경로·고도·폭·노면·좌우 경계·체크포인트·리스폰 위치·AI 기준선을 함께 둔다. 메시·충돌체·랩 판정이 서로 다른 옛 데이터를 참조하지 않게 한다. 연석 접합부와 경사 연결은 시각/물리 모두 검수한다.

AI는 기준선을 따라 스로틀·브레이크·조향 입력을 만들어 플레이어와 같은 컨트롤러에 전달한다. 곡선상의 좌표로 강제 이동하지 않는다. 랩은 동일 체크포인트 순서와 통과 방향으로 판정하고, 고스트에는 충돌을 만들지 않는다.

## 7. 새 코드 구조와 구현 규칙

기존 런타임을 ZIP에서 통째로 가져오지 않는다. 유지 중인 React·Three.js·Rapier·Vite를 이용해 필요한 책임부터 작은 모듈로 작성한다. 첫 버전은 현행 JavaScript 모듈과 JSDoc으로 시작하며 TypeScript 전환을 제작 선행 조건으로 만들지 않는다.

| 위치 제안 | 소유 책임 |
|---|---|
| src/app/ | 차고·경기·결과·로딩·오류 화면 전환 |
| src/core/ | 시간, 입력, 이벤트, 자원 수명주기 |
| src/render/ | 렌더러, 조명, 재질, 카메라, 화질 옵션 |
| src/garage/ | 차고 배치·상호작용·카메라 프리셋 |
| src/vehicle/ | VehicleSpec, 외형 로드, 물리, 휠 동기화 |
| src/track/ | TrackSpec, 메시/충돌 생성, 체크포인트 |
| src/race/ | 경기 상태, 시간, 랩, AI, 고스트 |
| src/storage/ · src/audio/ | 버전 저장, 설정과 소리 |
| tests/ | 순수 상태/동역학 시험, 장면 검수 절차 |

렌더 프레임마다 React 상태를 전체 갱신하지 않는다. 차고를 떠날 때 GPU 자원을 정리하고, 경기에서 나올 때 물리 월드와 입력·오디오 연결을 해제한다. 비동기 모델 로딩 중 장면을 바꾸면 이전 장면으로 모델이 늦게 붙지 않도록 취소/세대 검사를 둔다.

차고는 필요한 에셋부터 로드하고 출전 시 트랙 자원을 로드한다. 저장 키는 새 버전으로 분리하고 옛 브라우저 기록은 건드리지 않는다. 개인 기록에는 trackVersion/physicsVersion을 포함한다.

## 8. 품질 판정과 성능 예산

아래는 초기 목표다. 기준 PC/GPU·브라우저를 먼저 기록하고 측정 전에는 달성이라고 쓰지 않는다.

- PC: 1920×1080, 60FPS 목표. 워밍업 후 60초 구간의 평균 프레임 시간과 p95를 함께 기록하며 초기 p95 목표는 20ms 이하다.
- 저사양/모바일: 그림자·DPR·반사/후처리를 단계적으로 낮춘다. 모바일 30FPS 목표는 실제 기기에서 별도 검증하며 PC 창 축소로 대체하지 않는다.
- 로딩: 최초 차고 필수 전송량은 압축 후 8MB 이하를 초기 예산으로 삼되 실제 자산 검수 후 조정한다. public의 보존 파일 총량과 실제 요청량을 구분한다.
- 반복: 차고↔경기 10회 왕복 시 모델/텍스처/물리 자원이 지속 증가하지 않는지 본다.
- 주행: 30/60/120FPS 입력 스케줄에서 같은 고정 틱 물리 상태를 비교하고 차이가 나면 원인을 기록한다.

미술 검수는 고정된 차고 3/4·앞·뒤·측면, 중립 조명, 경기 후방·코너·역광 구도로 반복한다. 차체와 타이어 구분, 유리 투명도, 네 바퀴 접지, 깜빡임/관통, UI 가독성, 주행 시 코너 출구 시야가 필수다.

고품질 후보 차고에서 정교한 반사 비용이 크면 반사만 단순화한다. 반사를 낮췄을 때 장면 전체가 무너지면 형태·조명으로 돌아간다. FPS를 맞추려고 차체 디테일과 휠 접점을 먼저 지우지 않는다.
