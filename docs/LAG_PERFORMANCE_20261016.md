## 범위와 현재 판정

사용자가 로컬 여수 주행의 심한 끊김을 보고했다. 같은 작업 브랜치에서 기존 AI·충돌 수정은 보존하고 반복 상태 조회와 출발 준비 순서만 수정했다. 물리 계수, 조향, AI 페달 판단, 맵·차량 모델, 그림 품질, 교통량은 바꾸지 않았다. 운영 배포·커밋·푸시는 하지 않았다.

**전체 486/486 시험과 빌드, 실제 여수 6대 완주를 통과했다. 최종 여수 낮음/높음·남악 낮음 30초 측정은 모두 p95 16.9ms였다.** CPU 중복 작업은 줄었지만 전체 프레임 지연을 완전히 해결했다고 단정하지 않는다.

## 확인한 원인과 수정

### 1. 공유 물리 월드에서 사용하지 않는 상태를 생성

기존 `step(input, false)`는 차량 힘을 계산한 직후 상태 전체를 반환했지만 런타임·교통·헤드리스 레이스는 이 반환값을 버렸다. 공통 월드 계산 뒤 `finishStep()`에서 같은 상태를 다시 읽었다. 각 조회는 Rapier WASM 경계를 넘고 바퀴별 객체를 생성했다.

- 명시적 `prepareStep(input)`을 추가해 힘 계산만 수행하고 공통 월드 계산 뒤 한 번만 상태를 읽는다.
- 기존 `step(input, false)`의 상태 반환 계약은 유지한다.
- 한 상태 안에서도 바퀴 접촉·서스펜션 길이를 각각 한 번만 조회한다. 모든 결과 필드는 유지한다.
- 4바퀴 접지 상태의 상태용 바퀴 조회는 물리 스텝당 88회(44회 × 중간/완료)에서 28회로 줄었다. **다른 물리 계산까지 68% 감소했다는 의미는 아니다.** 낮음 여수의 8대/120Hz에서는 초당 57,600회의 불필요한 바퀴 조회를 피한다.
- 실제 수정 전 파일을 불러 8종 × 1,800스텝의 모든 상태 필드를 엄격 비교했다. 가속·벽 충돌·제동·핸드브레이크·후진·양방향 조향이 포함됐고 14,400스텝 모두 동일했다. 차종별 충돌 반응 발생 79스텝도 포함한다.

### 2. 출발 중 포커스 상실 시 준비 화면 고착

GPU 검사 준비 중 `phase=ready`, `paused=true`, `frameBoundary.pending=true`를 재현했다. 일시정지 화면의 그리기 생략이 첫 유효 프레임 경계보다 먼저 처리돼, 첫 프레임을 수락하지 못하고 재개 버튼까지 차단됐다.

준비 완료 → 유효 프레임 수락 → 일시정지 그리기 생략 순서로 바꿨다. 첫 프레임에서는 화면 캐시를 무효화한다. 포커스 상실 자체의 일시정지·입력 해제 동작은 유지한다. 재현 상태는 `start-focus-block.json`, 화면은 저장소 외부 `.work/lag-fix-20261016/screens/start-focus-before.png`에 보존했다.

`qaProfile=1`의 별도 실제 여수 주행 16개 GPU 샘플은 3.699~5.355ms, 마지막 표본은 전체364호출/837,104삼각형 중 차량323호출/782,292삼각형이었다. GPU 시간은 비동기 타이머로 읽었고 invalid/skipped/pending은 0이었다. 정지 차고 표본은 별도로 보존하고 주행값으로 사용하지 않았다. 이 국소 표본만으로 모든 구간의 GPU 비용이 낮다고 단정하지 않는다. 근거 없이 모델을 단순화하거나 교통을 삭제하지 않았다.
