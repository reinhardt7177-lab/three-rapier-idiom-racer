# 프레임 최적화 설계·실행 계획

## 목표와 경계

2026-11-03 사용자의 끊김 최적화 요청. 현재 Game Studio 적용본을 기준으로 같은 브랜치에서 진행한다. 물리120Hz·접지·충돌·AI 페달·메달·교통량·그래픽 품질 예산은 유지한다. 렌더 품질을 한꺼번에 낮춰 성공으로 표시하지 않는다. 로컬 검수이며 새 배포/PR/main 병합은 없다.

## 근거와 선택

- 실제 여수 높은 품질의 opt-in GPU query는 약5~8ms, 주행 CPU 물리/AI와 제출은 합계10ms 안팎이었다. 각 단계와 프레임 간격은 구분한다.
- `nearestRoute`는 매 물리 스텝 차량마다131점의 `Math.hypot`를 호출한다. 힌트 점의 정확한 거리를 상한으로 사용해 축 거리만으로 불가능한 후보를 제외한다. 최종 거리 계산과 순회 순서/동점 선택을 보존한다. 제곱 거리로 바꿔 반올림/오버플로 계약을 바꾸지 않는다.
- 초기 import의 오래된 해안 경로 계산도 프로파일에 나타났다. 선분에 투영한 뒤 축 하한으로 불가능한 후보만 제외해 반환값과 생성된 해안 충돌면을 유지한다. 이 비용을 주행 프레임 비용과 혼동하지 않는다.
- 차고는 자동 회전이 없는데 매 프레임 렌더한다. OrbitControls 변화·사용자 조작·자원 변경 때만 렌더한다. 주행 중 물리/AI의 빈도를 줄이지 않는다.

## 구현 순서

1. 변경 전 사본·기준 소스/프레임/GPU 프로파일과 실패 증거를 보존한다.
2. 경로 거리 검색의 기존 동점·힌트 fallback·큰 값·실제4코스 수천 위치를 기존 계산과 대조하는 실패 시험 및 계산 호출 예산 시험을 만든다.
3. 최소 수정 후 실제30초 레이스의 입력/위치 trace 일치와 계산 비용을 비교한다.
4. 차고의 첫 draw·안정 idle·drag damping·resize/품질/차종 변경·race 전환을 시험하고 브라우저에서 draw 수와 화면을 확인한다.
5. 독립 코드 검토 후 관련 시험+전체 npm run check를 격리된 동일 입력본에서 실행한다.
6. 무거운 검사 종료 후 같은IAB탭1280×720, 같은코스/품질/DPR/카메라/설정으로30초 A/B/A. 평균/p95/최대/>50ms/CPU 제출/진행거리/손실을 모두 남긴다. 별도 paused/garage 측정을 주행 FPS로 보고하지 않는다.
7. 실제 웹 빌드의 가속·조향·DRIFT·메뉴/회전·복귀·네 크기를 확인하고 새 문서/NEXT_STEPS에 수치·남은 위험을 기록한다.

기준: 같은 전체 단언 유지, 기존 완주·안정성 악화 시 관련 변경 보류. 같은 원인 세 번 초과 실패 시 확장을 멈추고 보고한다. Colab은 사용하지 않는다. 사용자 앱을 종료하거나 보안/전원 설정을 바꾸지 않는다.
