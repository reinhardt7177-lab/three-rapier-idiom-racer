# 브라우저에서 달리는 작은 레이싱 게임을 만들기까지

## MUMU CIRCUIT 제작기

처음 목표는 간단했다. 자동차를 고르고, 해안 도로를 달리고, 친구와 겨뤄 보는 게임을 만들고 싶었다. 하지만 차를 화면에 띄우는 것과 운전할 만한 게임을 만드는 일 사이에는 생각보다 많은 단계가 있었다.

개발 중 가장 자주 돌아온 말은 “차가 꿀렁거린다”, “핸들이 이상하다”, “여수가 여수 같지 않다”였다. 이 글은 그 문제들을 어떻게 나눠 고쳤는지 정리한 기록이다. 완성도를 과장하기보다 실제로 만든 부분과 아직 확인이 필요한 부분을 함께 남겼다.

## 1. 초기 화면에서 순수 웹 게임으로

![초기 주행 화면](images/01-early-driving.png)

초기에는 주행 화면과 항구 차고부터 만들었다. 이후 Unity로 제작·실험하던 시기를 거쳐, 설치 없이 실행하는 웹 게임으로 방향을 정했다. 최종 기반은 **Blender + Three.js + Rapier**다.

Unity에서 사용하던 선택된 메시·재질·해안 경로는 남아 있던 실행 자료에서 추출해 웹으로 옮겼다. 원래 C# 게임 코드나 삭제된 Unity 제작 프로젝트 전체를 복구한 것은 아니다. 복구 차량은 표면이 찌그러지거나 일부가 뒤틀리는 문제가 있어, 현재 차량은 Blender에서 다시 구성한 메시로 교체했다.

위 초기 사진은 Git 이력에서 복구한 웹 프로토타입이다. 사라진 Unity 작업 화면을 되살린 것처럼 소개하지 않는다.

![초기 항구 차고](images/02-early-harbor-garage.jpg)

## 2. 3D 작업과 게임 코드를 나눴다

Blender는 차와 도로를 만드는 작업실, Three.js는 브라우저에 그 결과를 그리는 도구, Rapier는 바퀴와 도로의 접촉·차량 충돌을 계산하는 도구다. React는 차고, 설정, 경기 결과 같은 화면을 맡는다.

```text
실차·지역 자료 → Blender 원본(.blend)
                     ↓ 제작·수출 스크립트
                 웹용 모델(.glb) + 경로 JSON
                     ↓
React UI → Three.js 화면 + Rapier 주행·충돌
                     ↓
                 Vite 웹 빌드 → Vercel
```

작업 원본과 게임에 넣는 파일은 따로 보관했다. 모델은 GLB로 수출하고 Draco 압축으로 전달 용량을 줄였다. 큰 해안 원본은 Git LFS로 관리한다. 사이트에서 실행되는 파일과 편집용 Blender 원본을 혼동하지 않는 것이 재작업의 출발점이었다.

## 3. 자동차는 도장보다 구조가 먼저였다

![Blender 차량 차고](images/03-eight-car-garage-v6.png)

현재 차고에는 수프라, SLK, 머스탱, 911, GT-R, RX-7, M3, 우라칸을 참고한 8종이 있다. 제조사 공식 모델이나 정밀 실차 스캔은 아니다. 실루엣·램프·휠·도장·유리의 차이를 담으려 한 자체 게임 모델이다.

차 전체를 한 덩어리로 움직이면 바퀴까지 차체와 함께 흔들렸다. 그래서 차체, 바퀴 회전, 앞바퀴 조향, 서스펜션, 실내 핸들을 나눴다. 여기서의 리깅은 사람 뼈대를 붙이는 작업보다 **기계 부품별 회전축을 정하고 실제 조작값을 연결하는 작업**에 가깝다.

후반에는 실차 자료와 앞·뒤·옆 모습을 비교했다. 도장 반사만 강하게 만드는 대신 검은 유리, 고무, 브레이크, 투톤 휠, 램프 렌즈를 각각 다듬었다. 수프라 전면을 크게 재성형한 후보는 램프 결함이 생겨 최종안에서 제외했다. 실패한 모양을 그대로 출시하지 않고 이전에 확인한 정렬로 복원했다.

![수프라 전후 비교](images/16-supra-polish-comparison.png)

## 4. “꿀렁거림”은 하나의 문제가 아니었다

도로 이음매에서 물리 차체가 튀는 문제, 보이는 메시가 뒤틀리는 문제, 카메라가 흔들리는 문제는 따로 확인해야 했다. 겉모습을 부드럽게 만들어도 충돌체가 튀면 운전감은 좋아지지 않는다.

물리는 고정 시간 간격으로 계산하고 도로 접촉과 차체 지지를 안정화했다. 그 뒤 가속·제동·선회에 반응하는 작은 기울기는 보이는 차체에만 주는 방식으로 분리했다. 바퀴의 접지 위치와 실제 충돌 자세를 장식 연출 때문에 바꾸지 않도록 했다.

운전감 개선에는 계측도 필요했다. 조향각만 늘린 중간 후보에서는 타이어가 버티지 못하는 현상이 나타나 속도대별 접지와 함께 다시 비교했다. 고속 카메라는 차량과의 상대 거리가 계속 벌어지지 않게 했고, 실내 핸들은 화면에서 보는 방향과 실제 조향 방향이 맞는지 확인했다.

“도로에서 안정적이다”와 “사람이 운전하기 재밌다”는 같은 결론이 아니다. 자동운전 시험을 통과한 뒤에도 사람이 연속 코너와 재추월을 평가하는 과정은 남아 있다.

## 6. 한 바퀴 이후에도 다시 달릴 이유

플레이어와 AI 5대의 레이스에 난이도·1랩/3랩·메달·기록·고스트를 연결했다. 전남 챔피언십에서는 남악 → 여수 → 성삼재를 달리고 순위별 10/6/4/3/2/1점을 누적한다. 라이벌은 성격에 따라 제동·추월·니트로 사용을 달리한다. 경기 거리를 순간적으로 늘려 주는 방식으로 속도를 맞추지 않는다. 사고 후 안전 복귀 기능은 별개의 안정성 보조다.

![챔피언십 결과](images/09-championship-result.png)

비 날씨에는 접지 감소·시야·물보라가 연결되고, 그래픽 설정에는 그림자·픽셀 비율·장식 거리·고스트 표시를 묶었다. 여러 기능을 켰다는 사실보다 낮은 품질에서도 읽을 수 있는 도로와 끊기지 않는 입력이 우선이었다.

BGM은 현재 **Seven Mile Horizon**과 **Slipstream Pursuit** 두 곡을 선택한다. Gemini에서 따로 만든 코스별 4곡의 원본도 보관했지만 아직 게임에 연결하지 않았다. 보관된 음악을 현재 플레이 중인 음악처럼 설명하지 않는다.

## 7. 운전석과 HUD를 함께 다듬기

![현재 운전석](images/17-current-cockpit.png)

운전석은 Blender 공통 모델에 실제 조향·속도·RPM을 연결했다. 차량별 실내 8종을 정밀 복제한 것은 아니다. 1인칭에서는 큰 차체 기울기를 그대로 카메라에 전달하지 않도록 제한하고, 속도·순위·방향 안내와 운전석이 도로를 지나치게 가리지 않는지 봤다.

가로 화면 1280×720, 1024×768, 844×390, 667×375를 반복 확인했다. QR은 좁은 세로 창에서 하단이 잘려 별도의 전체 창 레이어로 옮겼다. 이 크기 검사는 데스크톱 브라우저 크기 변경으로 수행한 것이며 휴대폰 실기기 검수라는 뜻은 아니다.

## 8. 친구와 온라인 1:1

![친구 대기실](images/19-online-friend-lobby.png)

온라인은 친구에게 초대 주소를 보내는 방식이다. 방장이 두 차량의 실제 물리를 계산하고 친구의 페달 입력을 받아 같은 세계에서 충돌과 결승을 판정한다. PeerJS가 연결 중개를 돕고 실제 경기 데이터는 WebRTC로 주고받는다.

연결이 됐다는 한 장면만으로 끝내지 않았다. 참가 확인·출발 준비 시간 초과, 밀린 통신 버퍼, 이전 경기 메시지, 일시정지 중 입력, 뒤늦게 도착한 연결 결과를 따로 처리했다. 최종 두 브라우저 창의 남악 완주는 **75.9917초 / 76.9167초**, 양쪽 시간·승패 일치와 복귀 0회를 확인했다. 이것은 같은 PC의 두 창 시험이다.

![QR 초대 화면](images/20-qr-invitation.png)

긴 방 코드를 손으로 옮기는 대신 QR을 더했다. QR은 외부 이미지 서비스로 초대 주소를 보내지 않고 브라우저에서 만든다. 생성기는 QR 버튼을 누른 뒤에 불러와 초기 주행에 불필요한 일을 더하지 않는다. 위 사진 속 방은 종료된 검수용 방이므로 실제 초대에는 새 방을 만들어야 한다.

친구 초대와 임의 상대 자동 매칭은 다르다. 현재 게임에는 공개 매칭 대기열·전용 공정성 서버·호스트 이전이 없다. 회사망, 다른 통신망, 실제 휴대폰 간 연결은 추가로 확인해야 한다.

## 9. 검증 기록도 결과물이다

최근 QR 마감 때 전체 검사 **475/475**, 시험 853.983초와 Vite 빌드 4.31초를 기록했다. 248개 실행 입력의 해시가 검사 중 바뀌지 않았는지도 확인했다. 당시 최종 산출물은 **37파일·80,107,952바이트**였고 QR 전용 청크는 gzip **8,035바이트**다. 전체 배포 파일 용량과 사용자가 첫 화면에서 받는 양은 다른 지표다.

프레임은 평균 FPS만 보지 않고 p95·최대·50ms 초과를 함께 남겼다. 특정 PC의 낮음 품질 표본이 좋았다고 모든 기기의 60FPS를 보장하지 않는다. QR 기능 검수를 새 그래픽 성능 측정으로 표현하지도 않는다.

이번 블로그 마감에서는 대표 이미지 20장만 작업 폴더에 남기고 나머지 일반 스크린샷과 임시 작업 사본을 정리했다. 수치·실패 기록·현재 모델·필수 시험 자료와 Git 이력은 보존했다. 상세 검증과 이번 정리 후 확인은 [마감 기록](../RELEASE_HANDOFF_20261016.md)에서 구분한다.

## 다음 한 가지

지금 가장 중요한 다음 작업은 기능을 더 늘리기보다 **두 실제 기기와 다른 통신망에서 친구 초대 → 출발 → 완주 → 재경기를 해 보는 것**이다. 모델의 매끈함, 코너의 재미, 지연 속 운전감은 자동 시험만으로 대신할 수 없다.

작은 레이싱 게임을 만드는 과정은 장식을 계속 추가하는 일보다, 어색하다는 한마디를 재현 가능한 문제로 바꾸고 다시 달려 보는 일에 더 가까웠다.
